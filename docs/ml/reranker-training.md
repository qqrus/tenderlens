# Обучение TenderLens-Reranker

Этот документ объясняет ML-часть проекта без предположения, что читатель уже знаком с
retrieval, fine-tuning или ранжированием.

## Какую проблему решает модель

Первый этап RAG быстро находит несколько потенциально подходящих фрагментов PDF. Вместе с
правильной цитатой в этот список часто попадают фрагменты с похожими словами, но другим
смыслом. Например, «обеспечение заявки — 2%» и «обеспечение исполнения договора — 5%».

Reranker получает пару `вопрос + фрагмент` и выдаёт score релевантности. Он применяется только
к небольшому списку кандидатов, поэтому может читать вопрос и текст совместно и работать
точнее, чем быстрый поиск по embeddings.

```text
PDF chunks -> hybrid retrieval top-20 -> TenderLens-Reranker -> top-5 -> answer model
```

Мы используем
[`cross-encoder/mmarco-mMiniLMv2-L12-H384-v1`](https://huggingface.co/cross-encoder/mmarco-mMiniLMv2-L12-H384-v1)
как исходную multilingual-модель и дообучаем её на примерах TenderLens. Это называется
domain adaptation: языковые знания уже находятся в модели, а мы учим её различать типичные
тендерные формулировки.

## Что находится в датасете

[`evals/reranker_seed_v1.jsonl`](../../evals/reranker_seed_v1.jsonl) содержит 32 вопроса,
128 пар `вопрос + фрагмент` и восемь полностью синтетических документов:

| Split | Документов | Вопросов | Для чего используется |
| --- | ---: | ---: | --- |
| train | 4 | 16 | обновление весов модели |
| validation | 2 | 8 | выбор настроек и контроль переобучения |
| test | 2 | 8 | однократный финальный экзамен |

В наборе 20 русских и 12 английских вопросов. Каждая запись содержит:

- `positive` — правильный фрагмент;
- `negatives` — три похожих, но неправильных фрагмента;
- `document_id` — идентификатор синтетического документа;
- `split` — часть датасета;
- `category` — тип условия: срок, бюджет, штраф, гарантия и другие.

Валидатор запрещает помещать один документ в несколько split. Без этого модель могла бы
увидеть формулировки одного PDF во время обучения и затем «сдать экзамен» на том же документе.
Такая утечка данных создаёт красивые, но недостоверные метрики.

## Что означают метрики

- `Hit@1` — как часто правильная цитата занимает первое место.
- `Hit@3` — как часто она находится хотя бы в первой тройке.
- `MRR` — насколько близко к началу списка стоит первый правильный результат.
- `nDCG@3` — качество позиции правильного результата в top-3.
- `mean_positive_rank` — средняя позиция правильной цитаты; здесь меньше — лучше.

Скрипт также сохраняет список ошибок с неправильным top-фрагментом. Это нужно для error
analysis: мы видим не только итоговый процент, но и конкретные понятия, которые путает модель.

## Проверка датасета без нейросети

```powershell
uv run python scripts/evaluate_reranker.py
```

Команда запускает lexical baseline — простое совпадение слов. Он не скачивает модели и
проверяется в GitHub Actions. На test split его `Hit@1` равен 0.625: пять правильных первых
мест из восьми.

## Установка ML-зависимостей

```powershell
uv sync --dev --extra ml
```

Optional-группа `ml` устанавливает PyTorch, Sentence Transformers, Datasets и Accelerate.
Обычный backend и production Docker-образ эти тяжёлые библиотеки не получают.

## Оценка готовой базовой модели

```powershell
$env:HF_HUB_DISABLE_XET = "1"
uv run --extra ml python scripts/evaluate_reranker.py `
  --scorer model `
  --model cross-encoder/mmarco-mMiniLMv2-L12-H384-v1
```

Первый запуск загружает около 471 MB весов в локальный Hugging Face cache. Модель и кэш не
добавляются в Git. Если встроенный downloader зависает на Windows, веса можно скачать в
игнорируемую папку `models/` и передать путь через `--model`.

Готовый cross-encoder получил `Hit@1 = 0.875` на validation и `1.0` на test. Это означает,
что seed test слишком мал для доказательства улучшения после fine-tuning. Результат честно
зафиксирован в
[`evals/reranker_baseline_v1.json`](../../evals/reranker_baseline_v1.json), а не используется
как заявление о production-качестве.

## Smoke-обучение на Windows

```powershell
.\scripts\train-reranker.ps1 -MaxSteps 1
```

Один шаг проверяет весь технический путь:

1. примеры превращаются в пары с метками `1` и `0`;
2. модель считает ошибку (`loss`);
3. backpropagation вычисляет, какие веса отвечают за ошибку;
4. optimizer обновляет веса;
5. новая модель сохраняется в `models/`;
6. validation и test оцениваются повторно.

Локальный smoke-run получил loss `0.4252` и завершил учебный шаг примерно за 1.5 секунды на
CPU. После одного шага ranking-метрики не изменились — это ожидаемо и не является неудачей:
smoke-run проверяет код, а не качество финальной модели.

## Первый трёхэпоховый эксперимент

После успешного smoke-run модель была обучена три эпохи на seed-наборе. Train Hit@1 вырос с
0.9375 до 1.0, но validation остался на 0.875. Единственная validation-ошибка сохранилась:
модель продолжила путать обеспечение заявки с обеспечением исполнения договора. Более того,
разница score между правильным и ошибочным фрагментами стала хуже.

Validation loss снизился с 0.1898 после первой эпохи до 0.117 после второй, а затем вырос до
0.1315. Это ранний сигнал переобучения: модель лучше запоминает train, но не улучшает ranking
на новом документе. Поэтому эксперимент получил решение `do_not_deploy` и зафиксирован в
[`evals/reranker_experiment_v0.json`](../../evals/reranker_experiment_v0.json).

Training pipeline теперь при полном обучении сохраняет checkpoint лучшей validation-эпохи,
а не автоматически оставляет последнюю. Отрицательный результат не скрывается: он показывает,
почему качество модели нужно подтверждать holdout-данными до интеграции в production.

## Полное обучение

Полный запуск технически доступен:

```powershell
uv run --extra ml python scripts/train_reranker.py `
  --epochs 3 `
  --batch-size 8 `
  --output-dir models/tenderlens-reranker-v1
```

Однако публиковать `v1` и заявлять улучшение пока рано. Сначала нужно расширить набор до
300–1000 вручную проверенных запросов, добавить hard negatives из реального hybrid retrieval
и увеличить test split. Иначе fine-tuning легко запомнит 16 учебных вопросов.

## Следующий ML-этап

1. Собирать только публичные или синтетические PDF без персональных данных.
2. Автоматически получать top-20 текущего поиска.
3. Размечать правильные фрагменты и самые опасные ошибки как hard negatives.
4. Довести набор минимум до 20–30 документов и 300 вопросов.
5. Сравнить базовую и дообученную модель на неизменяемом test split.
6. Интегрировать модель в FastAPI только при измеримом улучшении и приемлемой задержке.

В репозиторий попадут код, датасет, конфигурация и метрики. Сами тяжёлые веса должны
публиковаться отдельно как versioned model artifact, а не коммититься в Git.
